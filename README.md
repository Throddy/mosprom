# mosprom

Веб-сервис контроля нарушений техники безопасности по видео с камер. Нейросети YOLOv8n-pose и YOLOv8n квантованы в int8 и выполняются на ускорителе LinQ TPU, правила нарушений работают поверх детекций и трекинга, оператор получает тревоги и разбирает их в браузере. Кейс LinQ, хакатон «Открой#Моспром», 23–25 октября 2026.

## Нарушения

| `type` | Нарушение | Пункт кейса | Критичность | Как проверяется |
|---|---|---|---|---|
| `fall` | Падение и неподвижность | 07 | `critical` | корпус отклонён от вертикали по ключевым точкам, затем человек неподвижен |
| `danger_zone` | Человек в опасной зоне | 05 | `high` | точка ног (середина нижней грани бокса) внутри полигона зоны |
| `proximity` | Сближение с техникой | 02 | `critical` | расстояние от точки ног до бокса техники меньше заданного числа ростов человека |
| `running` | Бег в зоне работы техники | 01 | `high` | скорость человека в ростах в секунду, с учётом бега к камере и от неё |

Расстояние и скорость нормируются на высоту бокса человека, поэтому калибровка камеры не нужна. Событие создаётся, только если нарушение длится не меньше `min_duration`; одно нарушение одного человека даёт одно событие. Параметры по умолчанию и итоги подбора порогов: `backend/README.md`, раздел «Правила».

## Архитектура

```
камеры (файл, RTSP, папка кадров)
  -> backend: поток на камеру, последний кадр, общая очередь к детектору
  -> ml: детектор onnx (ONNX Runtime, CPU) или linq (LinQ TPU через ретранслятор)
  -> logic: трекинг ByteTrack, правила-плагины, min_duration, расписание
  -> backend: SQLite, снимок нарушителя, REST API, WebSocket /ws/events
  -> frontend: лента тревог, журнал, камеры, редактор зон, аналитика
```

| Каталог | Содержание | Владелец |
|---|---|---|
| `ml/` | детектор `create_detector()`, пре- и постпроцессинг, бэкенды `onnx` и `linq`, ретранслятор `ml.relay` | Анна Бабаева |
| `logic/` | трекинг, движок событий, правила в `logic/rules/` | Максим Волков |
| `backend/` | пайплайн камер, база событий, API по разделу 6 `CONTRACT.md` | Максим Волков |
| `frontend/` | интерфейс оператора: Vite, React, TypeScript | Никита Шульга |
| `core/` | общие типы `core/schemas.py` | Максим Волков |

Путь кадра на LinQ: JPEG до 640 px уходит через VPN и очередь RabbitMQ на ретранслятор рядом с TPU. Свёрточная часть обеих моделей считается на TPU в int8, декодирование боксов, сборка выхода и NMS выполняются на CPU. Граф разрезан, потому что при квантовании полного графа обнулялись уверенности ключевых точек. Подробно: `ml/README.md`.

Детектор выбирается переменной `DETECTOR_BACKEND`. Правила, база событий и интерфейс от неё не зависят: обмен идёт через API из `CONTRACT.md`.

## Интерфейс

| Раздел | Что делает | Задача |
|---|---|---|
| Лента тревог | события по WebSocket без перезагрузки, критичные первыми, снимок, камера, зона, время; решения «подтверждено», «ложное», «передано мастеру»; переподключение и досинхронизация после обрыва | FE-3 |
| Журнал событий | фильтры по типу, камере, зоне, статусу и времени, серверная пагинация, карточка события, ссылки на журнал из других разделов | FE-4 |
| Камеры | список камер, состояние из `/api/status`, видеопоток `/api/cameras/{id}/stream`, зоны и правила камеры | FE-4 |
| Зоны и правила | полигон зоны на кадре `/frame` (3–50 точек, координаты в долях кадра), формы правил по `GET /api/rules`, расписание, сохранение через `PUT /api/cameras/{id}` без перезапуска сервера | FE-5 |
| Аналитика | статистика `/api/stats`, метрики `/api/metrics`, замеры ONNX и LinQ из `/api/benchmarks`, калькулятор камер на плату, состояние камер | FE-6 |

В шапке показан детектор сервера из `/api/status`. В режиме `PIPELINE=0` интерфейс помечает события как тестовые.

## Установка

Нужны Python 3.10 и Node.js `^20.19.0` или `>=22.12.0`.

```bash
git clone https://github.com/Throddy/mosprom.git
cd mosprom
cp .env.example .env
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

На Windows интерпретатор окружения: `.venv\Scripts\python`. Особенности установки Python 3.10 на macOS и пакета `tpu_pycloud_format` для LinQ описаны в `ml/README.md`, раздел «Установка».

Фронтенд:

```bash
cd frontend
npm ci
npm run build
cd ..
```

Сборка попадает в `frontend/dist/`, бэкенд раздаёт её по `/`.

Веса для `PIPELINE=1` и детектора `onnx` в git не хранятся. Экспорт в `ml/weights/`:

```bash
mkdir -p ml/weights
cd ml/weights
../../.venv/bin/python -c "from ultralytics import YOLO; YOLO('yolov8n-pose.pt').export(format='onnx', imgsz=640); YOLO('yolov8n.pt').export(format='onnx', imgsz=640)"
cd ../..
```

## Запуск

Сервер: `python -m backend`, адрес `http://127.0.0.1:8000`. Переменные из `.env` сервер сам не читает, их нужно выгрузить в окружение:

```bash
set -a; source .env; set +a
```

Основные переменные (полный список в `backend/README.md`):

| Переменная | По умолчанию | Значение |
|---|---|---|
| `PIPELINE` | `1` | `1`: камеры обрабатываются детектором и правилами; `0`: тестовые события без детектора |
| `DETECTOR_BACKEND` | `onnx` | `onnx` или `linq` |
| `FIXTURE_WS_INTERVAL` | `10` | интервал тестовой тревоги при `PIPELINE=0`, с |
| `DB_PATH` | `backend/data/events.sqlite3` | база событий при `PIPELINE=1` |
| `CAMERAS_PATH` | `configs/cameras.local.yaml` | изменения камер из интерфейса; без этого файла камеры берутся из `configs/cameras.yaml` |

### Тестовые события

Без весов и детектора. API отдаёт 40 тестовых событий за последние 7 суток, новая тестовая тревога приходит раз в `FIXTURE_WS_INTERVAL` секунд.

```bash
PIPELINE=0 .venv/bin/python -m backend
```

### ONNX

Нужны веса в `ml/weights/`. Камеры `cam1` и `cam2` из `configs/cameras.yaml` читают `data/demo.mp4`.

```bash
PIPELINE=1 DETECTOR_BACKEND=onnx .venv/bin/python -m backend
```

### LinQ TPU

Нужны VPN LinQ, переменные `LINQ_*` в `.env`, программы TPU в `/auto/cache/<LINQ_LOGIN>/` и запущенный ретранслятор на сервере Jupyter (`notebooks/relay.md`). Ретранслятор работает, пока открыта вкладка Jupyter.

```bash
set -a; source .env; set +a
PIPELINE=1 DETECTOR_BACKEND=linq .venv/bin/python -m backend
```

Через облачный стенд кадр идёт 5–10 с, поэтому живой показ идёт на `onnx`, а LinQ показан замерами и офлайн-прогоном.

### Сайт

После `npm run build` сайт открывается на адресе сервера: `http://127.0.0.1:8000`. Для разработки:

```bash
cd frontend
npm run dev
```

Dev-сервер `http://localhost:5173` проксирует `/api`, `/ws` и `/media` на `http://localhost:8000`. `npm run preview` показывает сборку на `http://localhost:4173` с тем же проксированием.

## Офлайн-прогон и проверки

Прогон видео через детектор и правила без сервера, одна строка JSONL на событие:

```bash
.venv/bin/python scripts/run_offline.py --video data/videos/dev/fall.mov --camera test_fall --out /tmp/fall.jsonl
DETECTOR_BACKEND=linq .venv/bin/python scripts/run_offline.py --video data/videos/dev/fall.mov --camera cam2 --out /tmp/fall_linq.jsonl --fps 3
```

Камеры `test_*` для видео подбора порогов описаны в `configs/cameras.test.yaml`. Для `linq` переменные `.env` должны быть в окружении.

Все скрипты ниже, кроме `check_logic.py`, создают детектор `onnx`: нужны зависимости из `requirements.txt` и веса в `ml/weights/`.

| Команда | Что проверяет |
|---|---|
| `python scripts/smoke.py` | `data/demo.mp4` на `onnx`: у `cam1` одно событие `fall` и одно `danger_zone`, у `cam2` одно `fall` и ни одного `running`; при успехе `smoke: ok` |
| `python scripts/eval_offline.py --labels ... --videos ...` | подбор порогов: видео против разметки, события, tp, fp, fn, задержка тревоги; без аргументов скрипт читает `data/videos/test/` и `data/videos/test/labels.csv` |
| `python ml/metrics.py --videos data/videos/test --events ... --out ...` | метрики ML-7 на контрольном наборе: precision и recall по типам из файлов событий `run_offline`, разметка по умолчанию `data/test_set/labels.csv` |
| `python scripts/check_api.py` | API бэкенда |
| `python scripts/check_logic.py` | трекер и движок событий на синтетических детекциях |
| `python scripts/check_rules.py` | правила на синтетике и `data/demo.mp4` |
| `python scripts/check_pipeline.py` | пайплайн без сервера |
| `python scripts/check_events.py` | реальные события: пайплайн, база, снимки, API и WebSocket |
| `python scripts/check_cameras.py` | `PUT /api/cameras`: проверка, сохранение, применение без перезапуска |
| `python scripts/bench_cameras.py` | несколько камер на `onnx`: кадров/с, задержка обработки и до `event_new`, загрузка CPU |
| `python ml/bench.py` | замеры `onnx` и `linq`, результат в `reports/benchmarks.json`; для `linq` нужны переменные `.env` |
| `npm run build` в `frontend/` | проверка типов TypeScript и сборка |

Аргументы скриптов: `backend/README.md`, раздел «Скрипты», и `ml/README.md`.

## Результаты

Источники: `reports/benchmarks.json`, `reports/metrics.json`, `ml/README.md`, `backend/README.md`, `notebooks/e2e_linq.md`.

### LinQ TPU и ONNX

| Замер | Значение |
|---|---|
| Компиляция | `yolov8n-pose` и `yolov8n` в int8 под `TPU_H1M`, свёрточная часть на TPU, хвост графа на CPU |
| Совпадение с `onnx` | средний IoU боксов 0.950, минимальный 0.892, 20 кадров, 40 пар; без пары 6 из 46 объектов `onnx` |
| Время ускорителя, pose и det | 91.1 мс на кадр, без пре- и постобработки, сети и очереди |
| LinQ через облачный стенд | 0.80 кадра/с при 8 процессах ретранслятора и 8–16 потоках, было 0.26 при 1 процессе; задержка одного кадра 5–10 с |
| ONNX Runtime, CPU Apple M4, pose и det | 8.07–8.74 кадра/с на 1–8 потоках |

Расчёт по времени ускорителя: камер на одну плату `floor(10.98 / частота)`, это 5, 3, 2 и 1 камера при 2, 3, 5 и 10 кадрах/с. При 3 кадрах/с площадке на 50 камер нужно 17 плат. Сеть и очередь облачного стенда в этот расчёт не входят. Экономика внедрения: `reports/economics.md`.

### Обнаружение

| Прогон | Результат |
|---|---|
| Предварительный прогон ML-7, `fall`, `onnx`, 3 видео, которые теперь относятся к dev, до подбора порогов | tp 1, fp 0, fn 0; тревога через 5.5 с после начала падения; 0 ложных тревог на 43 с видео без падений |
| BE-11, видео dev, после подбора порогов | `fall` tp 1, задержка 3.5 с; `danger_zone` tp 1, 0.9 с; `running` tp 1, 3.3 с; fp 0, fn 0 |
| ML-4d, `fall.mov` (dev) на LinQ через ретранслятор, 3 кадра/с | падение найдено, тревога через 6.2 с после начала падения; на `onnx` при 10 кадрах/с 5.5 с |

Метрики на контрольном наборе `data/videos/test/` с разметкой `data/test_set/labels.csv` ожидают пересчёта ML-7. Сейчас `reports/metrics.json` содержит предварительный прогон из первой строки таблицы.

Задержка тревоги в основном состоит из ожидания правила: для `fall` это проверка неподвижности, заданная против ложных тревог.

### Производительность сервера

Детектор `onnx` на CPU Apple M4 Pro, видео `data/demo.mp4`: одна машина держит 2 камеры при 10 кадрах/с на камеру и 4 камеры при 5 кадрах/с. Обработка от кадра до `event_new` при 2 камерах: p50 69.7 мс, p95 90.9 мс. Таблицы: `backend/README.md`, раздел «Производительность».

## Ограничения

- Живые тревоги на LinQ через облачный стенд не успевают за видео: 0.80 кадра/с и 5–10 с на кадр. Очередь сервиса общая для всех команд.
- Имеющиеся метрики посчитаны на видео dev, по которым подбирались пороги, поэтому они не являются независимой оценкой. Метрики на контрольном наборе ожидают пересчёта ML-7.
- В контрольной разметке нет `proximity`: видео с погрузчиком `proximity.mp4` относится к dev.
- Модели не дообучались. Погрузчик детектируется классом COCO `truck`.
- `proximity` срабатывает и рядом с припаркованной техникой: движение техники не учитывается.
- Расхождения `linq` и `onnx` приходятся на объекты с уверенностью 0.41–0.58 у порога 0.4.
