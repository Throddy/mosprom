## Запуск

Проверено клоном с нуля на macOS (BE-13). Нужны Python 3.10 и Node.js `^20.19.0` или `>=22.12.0`. Команды выполняются из корня репозитория.

```bash
cp .env.example .env
python3.10 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Если `python3.10` нет, подойдёт любой интерпретатор 3.10: проверить `python3 --version`. Установка пакетов занимает около 5 минут.

Веса детектора `onnx` (около 1 минуты, скачиваются с GitHub Ultralytics):

```bash
mkdir -p ml/weights
cd ml/weights
../../.venv/bin/python -c "from ultralytics import YOLO; YOLO('yolov8n-pose.pt').export(format='onnx', imgsz=640); YOLO('yolov8n.pt').export(format='onnx', imgsz=640)"
cd ../..
```

Фронтенд:

```bash
npm --prefix frontend ci
npm --prefix frontend run build
```

Сервер. Переменные из `.env` сервер сам не читает, их нужно выгрузить в окружение:

```bash
set -a; source .env; set +a
.venv/bin/python -m backend
```

Адрес: `http://127.0.0.1:8000`, интерфейс оператора открывается там же. Камеры `cam1` и `cam2` читают `data/demo.mp4` по кругу, первое падение приходит в ленту примерно через 8 с.

Без весов и детектора, на тестовых событиях: `PIPELINE=0 .venv/bin/python -m backend`. API отдаёт 40 тестовых событий за последние 7 суток из `backend/fixtures.py`, новая тестовая тревога приходит раз в `FIXTURE_WS_INTERVAL` секунд.

## Переменные окружения

Все переменные, которые читает код, есть в `.env.example`.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `DETECTOR_BACKEND` | `onnx` | бэкенд детектора: `onnx` или `linq` |
| `PIPELINE` | `1` | `1`: реальные события, камеры обрабатываются детектором и правилами, события в базе `DB_PATH`; `0`: тестовые события в базе в памяти, тестовая тревога раз в `FIXTURE_WS_INTERVAL` с |

| `SOURCE_LOOP` | `1` | `0`: видеофайл и папка кадров не начинаются сначала после конца |

| `BACKEND_PORT` | `8000` | порт сервера |

## API

Пути, параметры и форматы JSON описаны в `CONTRACT.md`, раздел 6. Ошибки возвращаются HTTP-кодом и телом `{"detail": "текст"}`, ошибки валидации запроса — кодом 422.

- `GET /api/events`: `limit` от 1 до 500 (по умолчанию 50), `offset` не меньше 0.
- `PATCH /api/events/{id}`: `comment` не длиннее 1000 символов.
- `PUT /api/cameras/{id}`: проверки в разделе «Камеры».
- Если есть `frontend/dist/index.html`, сборка фронтенда раздаётся по `/`. Снимки событий сохраняются в `backend/media/` и раздаются по `/media/...`.

## Камеры

| Файл | Назначение |
|---|---|
| `configs/cameras.yaml` | базовые камеры, зоны и правила, хранится в git |
| `configs/cameras.local.yaml` | изменения из интерфейса через `PUT /api/cameras/{id}`, в git не попадает |

- При старте сервер читает `cameras.local.yaml`, если он есть, иначе `cameras.yaml`.
- `PUT` проверяет камеру, записывает все камеры в `cameras.local.yaml` (атомарно, через временный файл) и сразу применяет изменения к пайплайну и движку правил без перезапуска.
- Сбросить к базовым камерам: удалить `configs/cameras.local.yaml` и перезапустить сервер.

Проверки `PUT`. Ошибка даёт код 422 и `{"detail": "<ошибки через '; '>"}`:

| Поле | Правило |
|---|---|
| `id`, `name` | непустые строки, `name` до 100 символов |
| `fps` | число, `0 < fps <= 30` |
| `source` | `rtsp://...` или относительный путь внутри `data/` без `..`, файл или папка существует |
| `zones` | не больше 20 зон; `id` — непустые уникальные строки, `name` — строка до 100 символов, `polygon` от 3 до 50 точек, координаты — конечные числа от 0 до 1 |
| `rules` | не больше 20 правил |
| `rules[].type` | строка, правило есть в реестре (`GET /api/rules`) |
| `rules[].zone` | `null` или строка; у правила с `needs_zone` зона задана и есть в `zones`; заданная зона у других правил тоже должна быть в `zones` |
| `rules[].schedule` | `null` или две строки `HH:MM`, часы 0–23, минуты 0–59 |
| `rules[].params` | объект; только параметры из описания правила, значения — конечные числа от 0 до 1000 |

Значение не того типа даёт 422, а не 500. Чтение, изменение и запись камер в `PUT` выполняются под одной блокировкой, поэтому одновременные `PUT` не теряют изменений.

```bash
python scripts/check_cameras.py
```

## Пайплайн

Источник камеры задаётся полем `source`:

| Вид | Значение `source` | Чтение |
|---|---|---|
| Файл | путь к видео | в темпе реального времени с частотой `fps`, лишние кадры пропускаются |
| RTSP | `rtsp://...` | отдельный поток хранит последний кадр, переподключение каждые 2 с |
| Папка | путь к папке с `*.jpg`, `*.jpeg`, `*.png` | файлы по имени с частотой `fps` |

Относительные пути считаются от корня репозитория.

- На каждую камеру работает отдельный поток чтения, детектор работает в одном общем потоке.
- Детектор берёт последний кадр каждой камеры. Кадры, которые пришли, пока детектор занят, отбрасываются, поэтому отставание не накапливается.
- Если источник не открылся или закончился, камера получает `online: false`, повторное открытие через 5 с.

```bash
python scripts/check_pipeline.py
```

## События

- События движка правил сохраняются в SQLite (`DB_PATH`, папка `backend/data/` в git не попадает).
- Снимок события: кадр, на котором сработало правило, нарушитель выделен красным. Файл `backend/media/<camera_id>/<id>.jpg`, адрес `/media/<camera_id>/<id>.jpg`.
- Новое событие уходит в `/ws/events` как `event_new`, закрытие и смена статуса как `event_update`.
- При старте с `PIPELINE=1` события, открытые на момент прошлой остановки, закрываются: `ts_end = ts_confirm`.


## Скрипты

### `run_offline.py`

Прогон видео через детектор и правила без сервера, раздел 7 `CONTRACT.md`. Используется для метрик ML-7.

```bash
python scripts/run_offline.py --video PATH --camera ID --out PATH [--fps F] [--use-schedule]
```

| Аргумент | Значение |
|---|---|
| `--video` | видео `.mp4` или `.mov` |
| `--camera` | камера из `configs/cameras.yaml`: зоны и правила |
| `--out` | файл JSONL: одна строка на `Event` (`dataclasses.asdict`), по возрастанию `ts_confirm` |
| `--fps` | частота обработки, по умолчанию `fps` камеры |
| `--use-schedule` | учитывать `schedule` правил по текущему времени. Без флага расписание отключено, чтобы результат не зависел от времени запуска |

- Поля `ts_*` в выводе считаются в секундах от начала видео.
- События, открытые на последнем кадре, закрываются с `ts_end` последнего кадра.
- Детектор выбирается переменной `DETECTOR_BACKEND`.
- В stdout выводится итоговая строка: `<video>: <кадров> frames, <событий> events, <тип>=<число> ..., <секунд> s`.
- Если камеры нет или видео не открывается, код возврата 2.

## Правила

Движок `logic/engine.py` на каждый кадр обновляет треки (`supervision.ByteTrack`), вызывает правила камеры и превращает нарушения в события по разделу 5 `CONTRACT.md`.

Как добавить правило:

1. Создать модуль в `logic/rules/`, имя без `_` в начале.
2. Описать подкласс `Rule` из `logic/rules/base.py` с полями `type`, `title`, `severity`, `needs_zone`, `params`. В `params` обязателен `min_duration`.
3. Реализовать `check(ctx, cfg)`: вернуть `{track_id: extra}` для нарушителей в текущем кадре.

Модуль подхватывается автоматически, правило появляется в `GET /api/rules`.

| Константа | Значение | Смысл |
|---|---|---|
| `GRACE` | 1.0 с | кандидат удаляется, если нарушения нет дольше |
| `CLOSE_AFTER` | 2.0 с | событие закрывается, если нарушения или трека нет дольше |

```bash
python scripts/check_logic.py
```

Правила:

| `type` | Что проверяет | Параметры по умолчанию |
|---|---|---|
| `danger_zone` | точка ног человека (середина нижней грани бокса) внутри полигона зоны | `min_duration` 1.0 с |
| `fall` | корпус отклонён от вертикали (по плечам и бёдрам, без точек по пропорции бокса) и человек неподвижен | `min_duration` 1.5 с, `angle` 60.0 град, `aspect` 1.2, `still_window` 1.5 с, `still_tol` 0.3 длины тела |
| `proximity` | расстояние от точки ног человека до бокса техники (`car`, `truck`, `bus`, `forklift`), делённое на рост человека, меньше `dist`. Технику, в кабине которой находится человек, для этого человека не учитываем: это водитель. Водитель — точка ног внутри бокса техники, не меньше `inside_ratio` площади бокса человека внутри и точка ног выше нижнего края бокса техники не меньше чем на `cab_min` его высоты. Пешеход прямо перед техникой стоит на полу, его точка ног у нижнего края: он не водитель | `dist` 2.0 роста человека, `inside_ratio` 0.7, `cab_min` 0.15 высоты техники, `min_duration` 0.5 с |
| `running` | скорость за окно `window` больше `speed`: `v = sqrt(v_lat^2 + v_depth^2)`. `v_lat` — смещение точки ног (первая и последняя запись, без длины пути), делённое на рост человека и время. `v_depth` — бег к камере или от неё по изменению масштаба бокса: `r_h = ln(h_last / h_first)`, `r_w = ln(w_last / w_first)`; если знаки разные, 0, иначе `depth_k * min(abs(r_h), abs(r_w)) / dt`. Учитывается, только если человек стоит прямо во всех записях окна (угол корпуса меньше `upright_angle`, без точек высота/ширина бокса больше `upright_aspect`), иначе 0 | `speed` 1.5 роста человека/с, `window` 1.0 с, `depth_k` 5.0, `upright_angle` 30.0 град, `upright_aspect` 1.5, `min_duration` 1.0 с |

Расстояние и скорость нормируются на высоту бокса человека, калибровка камеры не нужна. Если у `proximity` или `running` задана `zone`, учитываются только люди с точкой ног в этой зоне.

`proximity` срабатывает и на человека, который стоит рядом с припаркованной техникой: движение техники не учитывается.

## Демо-стенд

Публичный стенд по ссылке: настройки `deploy/env.demo`, камеры `configs/cameras.demo.yaml`, развёртывание по шагам — `deploy/README.md`.

| Переменная | По умолчанию | На стенде | Значение |
|---|---|---|---|
| `READ_ONLY` | `0` | `1` | `PUT /api/cameras/{id}` и `PATCH /api/events/{id}` возвращают 403 `{"detail": "Демо-стенд: только просмотр"}` |
| `BLUR_FACES` | `0` | `1` | голова каждого человека пикселизируется на `/stream`, `/frame` и снимках событий: квадрат по точкам носа, глаз и ушей, без точек — верхние 22 % бокса |
| `MAX_STREAMS` | `30` | `30` | при стольких открытых `/stream` новый запрос получает 503 `{"detail": "Слишком много зрителей, попробуйте позже"}`; счётчик уменьшается, когда клиент закрыл поток |
| `STREAM_FPS` | `15` | `15` | частота кадров `/stream`. Камера читается с частотой `max(fps, STREAM_FPS)`, детектор получает не больше `fps` кадров/с камеры |
| `REMOTE_HOSTS` | пусто | список в `deploy/env.demo` | хосты, разрешённые в `source` с `http(s)://`: точное совпадение или поддомен. Пустой список — удалённые источники не принимаются. Адрес с логином и паролем не принимается |

Общий MJPEG: на каждую камеру один JPEG на все открытые `/stream`. Кадр сжимается один раз, когда пришёл новый кадр и есть хотя бы один зритель; лица размываются до сжатия. Зрители получают одни и те же байты, нагрузка не растёт с их числом. Лимит `MAX_STREAMS` действует как раньше.

Источники `source` кроме файла, RTSP и папки кадров:

- `http://` и `https://`, например HLS `.m3u8`: отдельный поток читает кадры и хранит последний, переподключение каждые 5 с;
- главный плейлист HLS: выбирается вариант с наибольшей высотой не больше 720, а если таких нет — с наименьшей. Плейлист одного варианта читается как есть;
- страницы YouTube (`youtube.com`, `youtu.be` и поддомены, по точному имени хоста): прямая ссылка на поток берётся через `yt-dlp`, при обрыве — заново, не чаще раза в 60 с. Если ссылку получить нельзя, камера `online: false`, причина один раз в логе;
- публичные камеры Ivideon `https://open.ivideon.com/embed/v3/<camera_id>/` (или `public.ivideon.com/camera/<camera_id>/`): ссылка на поток FLV берётся из openapi Ivideon (`backend/ivideon.py`), как у плеера на сайте, при обрыве — заново, не чаще раза в 60 с. Поток декодирует `ffmpeg` в 1280×720. Ссылка содержит токен: в лог пишутся только `camera_id` и хост, `ffmpeg` запускается без вывода.

## Известные ограничения

- Трансляции зависят от доступности источника; ссылки YouTube и Ivideon живут ограниченное время и обновляются автоматически.
- Трансляции «Терем Про» в варианте 720p отдают около 2 новых кадров/с с паузами до 3–4 с между сегментами HLS; на локальном стенде с шестью камерами частота обработки 0.4 кадра/с при заданных 2.

- Бег прямо на камеру без калибровки камеры не отличается от шага вблизи: рост рамки при шаге рядом с камерой совпадает с бегом вдалеке. На контрольном наборе бег к камере (`running_04.mov`) не находится.
- Бег со смазанным силуэтом не находится: детектор теряет человека в фазе бега (`running_03.mov`).
- `proximity`: человек, стоящий у припаркованной техники, даёт тревогу, движение техники не учитывается. Зона тревоги — 2 роста человека от бокса техники.
- Живые тревоги работают на `onnx`. LinQ представлен замерами (`reports/benchmarks.json`): через облачный сервис стенда кадр идёт 5–10 с.
- API без авторизации, CORS открыт для любого источника (требование `CONTRACT.md`, раздел 6). Сервер по умолчанию слушает только `127.0.0.1`.
