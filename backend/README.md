# Backend

Владелец: Максим. API описано в `CONTRACT.md`, раздел 6.

## Запуск

```bash
python -m backend
```

Адрес по умолчанию: `http://127.0.0.1:8000`.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `BACKEND_HOST` | `127.0.0.1` | адрес сервера |
| `BACKEND_PORT` | `8000` | порт сервера |
| `FIXTURE_WS_INTERVAL` | `10` | интервал тестовой тревоги в `/ws/events` при `PIPELINE=0`, с |
| `PIPELINE` | `1` | `1`: реальные события, камеры обрабатываются детектором и правилами, события в базе `DB_PATH`; `0`: тестовые события в базе в памяти, тестовая тревога раз в `FIXTURE_WS_INTERVAL` с |
| `DB_PATH` | `backend/data/events.sqlite3` | база событий при `PIPELINE=1`, путь от корня репозитория |
| `LOG_LEVEL` | `INFO` | уровень логов в консоли: `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `DETECTOR_BACKEND` | `onnx` | бэкенд детектора: `onnx` или `linq` |
| `SOURCE_LOOP` | `1` | `0`: видеофайл и папка кадров не начинаются сначала после конца |
| `CAMERAS_PATH` | `configs/cameras.local.yaml` | файл с изменениями камер из интерфейса |

Камеры читаются из `CAMERAS_PATH`, если файл есть, иначе из `configs/cameras.yaml`. Подробнее в разделе «Камеры».

Если есть `frontend/dist/index.html`, сборка фронтенда раздаётся по `/`. Снимки событий сохраняются в `backend/media/` и раздаются по `/media/...`.

## Камеры

| Файл | Назначение |
|---|---|
| `configs/cameras.yaml` | базовые камеры, зоны и правила, хранится в git |
| `configs/cameras.local.yaml` | изменения из интерфейса через `PUT /api/cameras/{id}`, в git не попадает |

- При старте сервер читает `cameras.local.yaml`, если он есть, иначе `cameras.yaml`.
- `PUT` проверяет камеру, записывает все камеры в `cameras.local.yaml` (атомарно, через временный файл) и сразу применяет изменения к пайплайну и движку правил без перезапуска.
- Сбросить к базовым камерам: удалить `configs/cameras.local.yaml` и перезапустить сервер.

Проверки `PUT`. Ошибка даёт код 422 и `{"detail": "<ошибки через '; '>"}`:

| Поле | Правило |
|---|---|
| `id`, `name` | непустые строки, `name` до 100 символов |
| `fps` | число, `0 < fps <= 30` |
| `source` | `rtsp://...` или относительный путь внутри `data/` без `..`, файл или папка существует |
| `zones` | `id` непустые и уникальные, `name` до 100 символов, `polygon` от 3 до 50 точек, координаты — конечные числа от 0 до 1 |
| `rules[].type` | правило есть в реестре (`GET /api/rules`) |
| `rules[].zone` | у правила с `needs_zone` зона задана и есть в `zones`; заданная зона у других правил тоже должна быть в `zones` |
| `rules[].schedule` | `null` или две строки `HH:MM`, часы 0–23, минуты 0–59 |
| `rules[].params` | только параметры из описания правила, значения — конечные числа от 0 до 1000 |

## Пайплайн

Источник камеры задаётся полем `source`:

| Вид | Значение `source` | Чтение |
|---|---|---|
| Файл | путь к видео | в темпе реального времени с частотой `fps`, лишние кадры пропускаются |
| RTSP | `rtsp://...` | отдельный поток хранит последний кадр, переподключение каждые 2 с |
| Папка | путь к папке с `*.jpg`, `*.jpeg`, `*.png` | файлы по имени с частотой `fps` |

Относительные пути считаются от корня репозитория.

- На каждую камеру работает отдельный поток чтения, детектор работает в одном общем потоке.
- Детектор берёт последний кадр каждой камеры. Кадры, которые пришли, пока детектор занят, отбрасываются, поэтому отставание не накапливается.
- Если источник не открылся или закончился, камера получает `online: false`, повторное открытие через 5 с.

```bash
python scripts/check_pipeline.py
```

## События

- События движка правил сохраняются в SQLite (`DB_PATH`, папка `backend/data/` в git не попадает).
- Снимок события: кадр, на котором сработало правило, нарушитель выделен красным. Файл `backend/media/<camera_id>/<id>.jpg`, адрес `/media/<camera_id>/<id>.jpg`.
- Новое событие уходит в `/ws/events` как `event_new`, закрытие и смена статуса как `event_update`.
- При старте с `PIPELINE=1` события, открытые на момент прошлой остановки, закрываются: `ts_end = ts_confirm`.

```bash
python scripts/check_events.py
```

## Скрипты

### `run_offline.py`

Прогон видео через детектор и правила без сервера, раздел 7 `CONTRACT.md`. Используется для метрик ML-7.

```bash
python scripts/run_offline.py --video PATH --camera ID --out PATH [--fps F] [--use-schedule]
```

| Аргумент | Значение |
|---|---|
| `--video` | видео `.mp4` или `.mov` |
| `--camera` | камера из `configs/cameras.yaml`: зоны и правила |
| `--out` | файл JSONL: одна строка на `Event` (`dataclasses.asdict`), по возрастанию `ts_confirm` |
| `--fps` | частота обработки, по умолчанию `fps` камеры |
| `--use-schedule` | учитывать `schedule` правил по текущему времени. Без флага расписание отключено, чтобы результат не зависел от времени запуска |

- Поля `ts_*` в выводе считаются в секундах от начала видео.
- События, открытые на последнем кадре, закрываются с `ts_end` последнего кадра.
- Детектор выбирается переменной `DETECTOR_BACKEND`.
- В stdout выводится итоговая строка: `<video>: <кадров> frames, <событий> events, <тип>=<число> ..., <секунд> s`.
- Если камеры нет или видео не открывается, код возврата 2.

### `smoke.py`

```bash
python scripts/smoke.py
```

Прогоняет `data/demo.mp4` через `run_offline` с камерой `cam1` на бэкенде `onnx`. Ожидается ровно одно событие `fall` и одно `danger_zone`, у обоих задан `ts_end`, у `fall` `ts_start` не меньше 3.0 с. При успехе печатает `smoke: ok` и возвращает код 0.

## Правила

Движок `logic/engine.py` на каждый кадр обновляет треки (`supervision.ByteTrack`), вызывает правила камеры и превращает нарушения в события по разделу 5 `CONTRACT.md`.

Как добавить правило:

1. Создать модуль в `logic/rules/`, имя без `_` в начале.
2. Описать подкласс `Rule` из `logic/rules/base.py` с полями `type`, `title`, `severity`, `needs_zone`, `params`. В `params` обязателен `min_duration`.
3. Реализовать `check(ctx, cfg)`: вернуть `{track_id: extra}` для нарушителей в текущем кадре.

Модуль подхватывается автоматически, правило появляется в `GET /api/rules`.

| Константа | Значение | Смысл |
|---|---|---|
| `GRACE` | 1.0 с | кандидат удаляется, если нарушения нет дольше |
| `CLOSE_AFTER` | 2.0 с | событие закрывается, если нарушения или трека нет дольше |

```bash
python scripts/check_logic.py
```

Правила:

| `type` | Что проверяет | Параметры по умолчанию |
|---|---|---|
| `danger_zone` | точка ног человека (середина нижней грани бокса) внутри полигона зоны | `min_duration` 1.0 с |
| `fall` | корпус отклонён от вертикали (по плечам и бёдрам, без точек по пропорции бокса) и человек неподвижен | `min_duration` 3.0 с, `angle` 60.0 град, `aspect` 1.2, `still_window` 2.0 с, `still_tol` 0.3 длины тела |
| `proximity` | расстояние от точки ног человека до бокса техники (`car`, `truck`, `bus`, `forklift`), делённое на рост человека, меньше `dist` | `dist` 1.0 роста человека, `min_duration` 0.5 с |
| `running` | смещение точки ног за окно `window` (первая и последняя запись, без длины пути), делённое на рост человека и время, больше `speed` | `speed` 1.5 роста человека/с, `window` 1.0 с, `min_duration` 1.0 с |

Расстояние и скорость нормируются на высоту бокса человека, калибровка камеры не нужна. Если у `proximity` или `running` задана `zone`, учитываются только люди с точкой ног в этой зоне.

Пороги `fall` подобраны на `data/demo.mp4` и уточняются в BE-11 на тестовых видео. `proximity` срабатывает и на человека, который стоит рядом с припаркованной техникой: движение техники не учитывается. Пороги `proximity` и `running` тоже уточняются в BE-11.

Если правило камеры не разбирается (например, неверное `schedule` или нечисловой параметр), движок пропускает только это правило и один раз пишет предупреждение в лог. Трекинг и остальные правила камеры работают.

```bash
python scripts/check_rules.py
```
